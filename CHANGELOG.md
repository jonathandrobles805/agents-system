# Changelog

All notable changes to the kit. Each entry names the decision or lesson that caused it.

## [0.3.0] - unreleased

### Fixed (hardening plan Step 1: the real-agent eval measured its own gaps, not the kit's agents)
- **The agents get the inputs their goals name.** The `eval-smoke-main` run after #103 (run 45081939311), with real agents, scored spec-critic, tester, implementer and reviewer 0.00; a run on the owner's Mac with full transcripts showed each agent stopping because the spec, lane or review file its goal named did not exist. Those four tasks now have a `setup`: an approved `truncate-text` spec that passes `validate_docs` (waiting approval for the critic), and for the tester, implementer and reviewer a lane made by `lane.js start` and moved on with `lane.js stage`, with real test runs through `lane.js check` recorded in progress.md (the implementer gets the tester's red test; the reviewer gets the committed change, its red and green runs and the review template). The kit's own done-check accepts that evidence. The feature is low-risk (a text module the setup adds; the spec names no high-risk path or keyword), so the lanes run the common path with no high-risk waiver.
- **Each task runs as the kit's agent.** The worker session now runs with `claude --agent <role>` when that agent is installed in the session's home, so the eval measures the kit's tester, implementer and so on, not plain Claude in a kit repo. The judge still runs as no agent. Lanes launch exactly as before.
- **A red run can be seen.** `red_before_green` looked for `event: 'test'`, which a Bash call is never logged as. The scorer now counts the post-edit hook's test runs, `kit lane check` runs, and Bash calls that run the project's recorded test command, red when Claude Code reported the call as failed; a piped, `;`/`||`-chained or backgrounded (`&`) command does not count, since its exit is not the test's, and an `&&` chain that goes on after the test counts only when it passed. Events are read from the lane's file and the session file the hooks use for what they cannot place in a lane. The implementer is credited with the tester's red run the setup recorded (its instructions say not to re-run it); its green run must be its own. The tester's task no longer expects a green run it is told not to produce: it checks for a red run and no source edits.
- **No check passes on the setup alone.** The reviewer's check passed the untouched review template the setup writes ("13 rows with evidence"); it now runs the kit's own review rules, so a placeholder or a Result other than PASS/FAIL fails. The retro's only check was that `LESSONS.md` exists, which bootstrap creates; it is now checked for the lesson entries it printed (the retro agent never writes `LESSONS.md` itself), each valid by the kit's lesson rules.
- **The judge grades the session, not the setup.** It is told which files the setup wrote and gets the session's own diff against the state the setup left, with what the session printed and the end state for context. The implementer's rubric no longer grades the test's name (the setup wrote that test).
- **Transcripts are kept.** Each worker and judge transcript is saved beside `report.json`, credential-looking strings redacted (Anthropic, GitHub classic and fine-grained, AWS key ids, Bearer and Slack tokens, `…password=`/`…secret=` values), and both CI eval jobs upload them with the report (30 days). The report also records the worker's command line, and warns when a task ran without its kit agent (the container runtime).
- **Quieter sessions.** The session's `ZDOTDIR` is its own home, so zsh no longer sources the owner's startup files with `HOME` moved (`.zshenv: no such file or directory: <home>/.cargo/env` on every Bash call). The lane's main repository is marked trusted too, which a worktree session needs for its `permissions.allow` rules to apply.

### Fixed (hardening plan Step 2, #63 part 2: the kit's gate commands in each project)
- **`kit.json` gate commands use the launcher.** `/bootstrap` wrote the kit's own gates as `node "$HOME/.claude/kit/scripts/ci_audit.js" --repo .` (audit, node stack) and `… ci_boundaries_simple.js --repo .` (boundaries), and generated allow rules in that same form, which Claude Code does not approve. They are now `kit ci_audit --repo .` and `kit ci_boundaries_simple --repo .`, covered by `Bash(kit *)`.
  - `/bootstrap --upgrade` migrates both "$HOME" forms (and the older `npm audit --audit-level=high`) as old kit defaults, and moves any other command that starts with a kit script in the "$HOME" form to `kit <script>`, its arguments kept; a project's own commands are kept, including another tool called `kit` (KitOps' `kit pack …`), which is never treated as stale.
  - The generated CI runs the checked-out kit: `kit <script>` at the start of a command, or after `&&`, `;` or `|`, becomes `node "$KIT_DIR/scripts/<script>.js"`, only when the kit has that script.
- **Proof:** the permission probe from #103, run on the owner's Mac (Claude Code 2.1.328, 2026-11-22), gave 7/7 as expected: `Bash(kit *)`, `git add`, `git commit` and `Edit(/**)` approved; the "$HOME" form and an unlisted command refused; `Bash(kit *)` approved through `--settings` in an untrusted repository.

### Fixed (hardening plan Step 2, #63: the kit's own commands were refused in unattended runs)
- **The `kit` launcher.** A probe with Claude Code 2.1.328 on macOS (2026-11-22) showed the kit's rule `Bash(node "$HOME/.claude/kit/scripts/*)` refused the identical command in a headless session, while `Bash(kitprobe *)` approved a plain command on PATH, also through `--settings` in a repository that was not trusted. So every kit script call an agent made unattended (`lane.js next-step`, `validate_docs`, …) was refused. Now:
  - `install.sh` writes `kit` into `~/.local/bin` (`KIT_BIN_DIR` overrides), pointing at the installed kit; it never replaces a `kit` it did not write, and warns when `kit` on `PATH` is not its launcher;
  - agents and skills run `kit lane next-step …`, `kit validate_docs …` (every kit script call, and the shorthand `lane.js <sub>` mentions, now `kit lane <sub>`); so do the refusal messages that tell an agent what to run next. Hook commands keep their `node "$HOME/…"` form, since hooks need no permission and must not depend on `PATH`;
  - the shipped rule is `Bash(kit *)`; `/bootstrap --upgrade` replaces the old one. A `Bash(kit …)` rule counts as the kit's only when it is the launcher rule or names a kit script, so a project's rules for another tool called `kit` survive;
  - `kit/scripts/permission_probe.js` (`npm run permissions:probe`) proves each shipped rule with Claude Code itself, plus controls (the `"$HOME"` form, an unlisted command) that must stay refused. Each verdict comes from Claude Code's own denial list for the exact call; no call, another command or a failed call is inconclusive and fails. A unit test keeps one case per shipped rule. The architecture manifest lists it as unreferenced: it is run by hand, with a credential, never in CI.
  - `install.sh` resolves a relative `CLAUDE_HOME`, keeps an `&` in it literal (bash 5.2), and the eval's install never follows the owner's `KIT_BIN_DIR`, so running the eval cannot overwrite the owner's launcher.
- **Templates without reading outside the project.** `kit lane template <goal|spec|research|review|lesson> [--slug S]` prints a kit template with the slug, date and commit filled in on its header lines; a `… by:` line (the spec's approval, the goal's agreement) keeps its placeholders for the person deciding. The agents used to read `~/.claude/kit/templates/`, which is outside the project and was refused in the real-agent eval (2026-11-22). The implementer no longer reads the progress template: `lane.js start` already writes the progress file.
- The architecture manifest reads the `kit <script>` and `kit lane template <name>` forms. The eval's sessions get the launcher first on `PATH`, write-denied.
- Not in this change (Step 2, next): the gate commands `/bootstrap` writes into `kit.json` (audit, boundaries) still use the `"$HOME"` form; narrowing the lanes' rules and the skills' `Bash`; `kit merge` behind an `ask` rule.

### Fixed (hardening plan Step 1: the real-agent eval could start its sandbox but no agent ever ran)
- **Claude Code runs inside the eval's sandbox, with the kit under test.** The first `eval-smoke-main` run that touched skills (after #101, run 44987376718) started the sandbox, and every session then exited. Each cause below was reproduced locally (srt 0.0.83, Claude Code 2.1.330) and is fixed in the `claude` runner:
  - the sandbox makes `/tmp` and `$HOME` read-only, so Claude Code could not create its temp directory (`EROFS: ... mkdir '/tmp/claude'`). Each session now gets its own home in the eval's scratch space, writable: `HOME`, Claude Code's config directory (`CLAUDE_CONFIG_DIR`, its `.claude`) and a temp directory beside it (`CLAUDE_CODE_TMPDIR`);
  - the kit was never installed where the fixture's hooks look (`$HOME/.claude/kit/scripts/...`), so on the runner every guard hook would crash and block nothing. The kit under test is now installed into that home (`install.sh --copy`), with its agents and skills; a guard hook run in the sandbox blocks again (exit 2, where it crashed before);
  - Claude Code ignored the fixture's 16 `permissions.allow` rules because the workspace was not trusted. The session's config marks the fixture repo trusted (`hasTrustDialogAccepted`), the only headless way Claude Code offers;
  - `api.anthropic.com` was not on the sandbox's network allowlist, so a session hung until its timeout. The eval adds it.
- The session cannot rewrite the kit's copy in its home: `kit`, `agents`, `skills`, `commands`, `settings.json` and `CLAUDE.md` there are write-denied (srt `denyWrite`, now passed through by `srtSettings`; lanes still pass none). The owner's own `~/.claude` and `~/.claude.json` are read-denied (if the `claude` program itself lives under `~/.claude`, the old local install, that one folder stays readable) and never written; the fixture's bootstrap registers the repo in the session's home. The judge gets a home of its own and an empty working directory, the only places it can write, so nothing the worker wrote (a `CLAUDE.md`, settings) reaches it. Git in the session commits as `kit-eval`. Still open (hardening plan Step 4, recorded in `bypass.test.js`): the repo's own `.claude/settings.json`, which registers the hooks, is writable in the worktree. Credentials still come from the environment. Two tests. srt only: the container runtime does not get these settings. Lanes are not changed: a lane session started in `srt` would need the same things, and that is not part of this fix.

### Fixed (hardening plan Step 2: #57, #58, #59 — work types that cannot finish are refused, never reported done)
- **Not built yet → refused.** Nothing runs the `inspect`, `report` and `verify-ui` stages, and the `skill-smith` agent does not exist. `lane.js next-step` used to map their stages forward to `done`, so a docs goal (any size) or a ui goal at S or M was reported finished without any work (#57). `next-step` and `lane.js start` now refuse docs, ui at S and M, investigation and skill-development with the reason; ui at L (the feature shape) and every other work type start where they did. Building them is on the hardening plan's to-do list (the owner chose to refuse now, build later).
- **No mapping to done.** A stage a profile lacks maps forward only to a stage the profile has (retro maps to done for a profile without retro); anything else is refused with the reason (#57).
- **`requires` blocks (#58).** A high-risk lane whose profile adds `security-signoff` stops at stage `security-signoff` instead of `wait-merge`, and `lane.js merge` refuses it until a sign-off is recorded; recording it comes with the store (Step 2). The PR's head branch is read from GitHub (whether the PR came from `--pr` or the slug's ROADMAP row): a `wt/<slug>` head names the lane, and a different slug on the command line is refused; a `spec/` or `goal/` PR is not a lane and needs no sign-off. **Behaviour change:** before, a high-risk feature or fix lane reached `wait-merge` with a `requires` nothing read and could be merged, and a security lane never got one; now every high-risk lane that needs a sign-off is blocked from merging until the store can record it.
- **The queue skips work kept for later.** `lane.js next` passes over an agreed goal whose work type is not built yet, so it does not hold the queue. The `/zi-run` table has a `security-signoff` row; `refused` names the new reasons; the four affected entry skills say they are not built yet.

### Changed (hardening plan Step 2, D3: the lane start fails closed on its base)
- **`lane.js start` refuses to start from a stale base.** A failed `git fetch` of the base from `origin` is refused (before, it silently fell back to the local branch). A repo with no `origin` is refused unless `.claude/kit.json` says `"local_only": true` (exactly `true`). The base is fetched with an explicit refspec (`+refs/heads/<base>:refs/remotes/origin/<base>`), so a narrowed remote refspec cannot leave `origin/<base>` stale; the worktree is created from that commit, and `lane.json` records `base_commit`. Nothing is created when the start is refused: no worktree, no lane branch, no change to the main checkout. Test fixtures without a remote set `local_only`; two tests and planted fault 51 cover the refusals and the recorded base.

### Fixed (`lane.js merge` under the agent-branch ruleset)
- On kit-test (Step 1's done-when), `lane.js merge` waited for every check to pass and then GitHub refused the merge: "the base branch policy prohibits the merge". The `kit agent branches` ruleset (#93) lets only the owner update the default branch, and a plain `gh pr merge` does not use the owner's bypass. `lane.js merge` now reads `enforce_admins` from GitHub after the checks are green and, when it is on, merges with `--admin`, which uses the ruleset bypass and nothing else: GitHub refused `gh pr merge --admin` on a pending PR in the same test ("10 of 10 required status checks are expected"). Without `enforce_admins` it never passes `--admin` and warns. Just before merging it reads the PR again and refuses if the base or head changed (`--match-head-commit` pins only the head). The unused `protection()` helper is replaced by `adminEnforced()`. One test covers enforce_admins on, off, unreadable, no protection, red CI and a base changed mid-merge.

### Fixed (eval: a real-agent run that never started was undiagnosable)

### Added (hardening plan Step 1, D1; 0016 E.7: the push is the App's, on the owner's machine)
- **`lane.js publish <slug> [--branch spec/<slug>] [--title T] [--body-file F | --body T] [--base B]`** pushes a lane or spec branch and opens its PR as the kit's GitHub App. New `kit/scripts/app_token.js` reads the App's id and private key from `~/.claude/kit-app.json` or `KIT_APP_ID` + `KIT_APP_PRIVATE_KEY` (a path outside every repository; a key inside one is refused), signs a ten-minute RS256 JWT and mints an installation token limited to that repository and to contents + pull requests. The token reaches git through `GIT_ASKPASS` with the owner's git configuration ignored (no `pushInsteadOf`, auth header or credential helper of the owner's can route the push through the owner's identity; a repository-local one is refused) and gh through `GH_TOKEN`, never a command line or the output; nothing in `publish` touches the network as the owner. `publish` refuses any branch but `wt/*` or `spec/*`, a branch not checked out, and uncommitted changes. `zi-implement`, `zi-run` and `zi-plan` call it in place of `git push` + `gh pr create`. Planted fault 50 checks that no skill pushes with the owner's login and that the token stays out of command lines. **Owner setup:** write `~/.claude/kit-app.json` with the App id and the key's path.

### Added (hardening plan Step 1, D1; 0016 E.7: the agents' identity stays on its branches)
- **`bootstrap --protect` creates two repository rulesets**, `kit agent branches` and `kit tags`: outside `wt/*` and `spec/*` no branch may be created, updated or deleted, and no tag may be, except by the one actor on the bypass list, the user `gh` is logged in as (`OrganizationAdmin` for an organization's repository). The GitHub App the agents push with is not on the list, so it can push lane and spec branches and nothing else. Rulesets are upserted by name (the merge-queue ruleset too), read back and compared; any difference fails the result with exit 1. Planted fault 30 now also checks what is sent and plants a second bypass actor, which is refused.

### Fixed (0016 E.11, hardening plan Step 1: a matrix job's check name)

### Fixed (#68, kit-test canary run: two PRs merged on red CI)
- **Merging now waits for CI.** `lane.js merge [<slug>] [--pr N] --by <name>` is the only way the kit merges: it waits until every required job of the project's workflow has reported on the PR head and passed, refuses red or pending CI, and squash-merges pinned to the checked head (`--match-head-commit`). "No checks reported", what `gh pr checks` says before CI starts, counts as pending, not green. `lane.js ci` shows the same state without merging. `/zi-run`, `/zi-start`, `/zi-plan` and `/zi-review` use them; the bash guard blocks `gh pr merge` and merging through `gh api`.
- **Branch protection required checks that never report.** `bootstrap --protect` required step names (`scope-diff`, `review-report`, …), which GitHub never reports as checks, so every PR would have waited forever. It now requires the workflow's job names, the same list `lane.js merge` waits for.
- After merging, `lane.js merge` warns when the base branch has no protection: a merge from the GitHub page is then not blocked on red CI. Private repositories need a GitHub plan that offers branch protection.
- Planted faults 47 (an agent merges directly) and 48 (no checks or one red check read as mergeable).
