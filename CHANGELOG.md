# Changelog

All notable changes to the kit. Each entry names the decision or lesson that caused it.

## [0.3.0] - unreleased

### Added (hardening plan Step 3: the gate, first part)
- **`kit lane gate <slug>` re-runs the recorded checks on the lane's HEAD and binds the verdict to that commit.** The checks are the ones CI runs on a pull request, from the **base branch's committed** `.claude/kit.json` (`origin/<base>`, or the local base when `local_only`), never the lane's copy (0016 E.1 Add 2; #56 S1.1). A check not recorded, empty, or `"none"` with no reason fails the gate; `"none: <reason>"` is off and reported as off (#56 S1.2). Each check runs contained through the lane's own launcher (srt; the container once its image is built in Step 8; otherwise `degraded`, recorded), as `sh -c` in the worktree with stdin closed, `CI=1`, no GitHub token, App key or Anthropic credential, and a per-check time limit (`gate_timeout_min`, default 20) that kills the whole process group (#56 S1.4). It refuses a worktree with uncommitted changes outside the lane's bookkeeping files. The verdict goes to the lane store (`gate`) and a report (`GATE: PASS|FAIL`, each check, the end of each failing check's output) to `.claude/session/lanes/<slug>.gate.txt`.
- **No reviewer starts without a gate PASS for the exact HEAD.** `advance` refuses build → review, and review → review, on no verdict, a FAIL, or a verdict for another commit (stale). `next-step` answers the new script stage `gate` when the lane is green with no current verdict, and `build` on a FAIL. `/zi-run` (new `gate` row), `/zi-review` (after a fail list) and `/zi-implement` run the gate; the reviewer is never spawned on anything but a PASS.
- **A gate FAIL ends the round (D2)**, counted once per commit, and parks the lane past `max_rounds` the same way a review FAIL does.
- Tests: `gate.test.js` (pass, fail with output, missing and bare `none`, a hanging check stopped with its children and a closed stdin, the base's kit.json over the lane's and the main checkout's, no credentials, uncommitted changes, no/FAIL/stale verdicts refused, parking). Existing tests that move a lane to review record a gate PASS (`fixtures.gatePass`), and assert next-step's `gate` stage before it. Planted fault 64: MISSED on main (a reviewer starts with no gate at all), CAUGHT here.
- Not yet (the rest of Step 3): the protected-file check and the risk re-check (D4), the re-run after updating from the base with a conflict parking the lane, and done-check reading the verdict.

### Changed (hardening plan Step 2, #63: the narrowing)
- **Lanes cannot move, gate, start or merge themselves.** An unattended lane (`kit lane launch`) and the real-agent eval's worker now get their grants per run, as `claude --settings <file>` (`sandbox.js runSettings`, from the new `kit/hooks/settings.lane.json`), because a headless session does not use a project's allow rules unless the folder was trusted. The file names only what the run needs: `Edit` inside its worktree, `git add`/`git commit`, the project's recorded commands and its role's kit commands. It denies `kit lane advance` (and `stage`), `gate`, `start`, `scope`, `finish`, `merge`, `merged`, `resume-all`, `signoff`, `launch` and `kit bootstrap`. Deny beats the project's allow rules. The bash guard refuses the same commands to a subagent (its calls carry `agent_id`) and to a launched lane (`KIT_LANE`), so the orchestrator in the main session keeps them.
- **`Bash(kit *)` is gone.** The project's settings name each kit command the skills run (`Bash(kit lane next-step *)`, `Bash(kit validate_docs *)`, …, and `Bash(kit lane gate *)`, kept free for the gate in Step 3). The broad rule approved every kit script and also a different tool called `kit` (KitOps). `/zi-bootstrap --upgrade` removes it. Merging stays behind its `ask` rule, and so do `resume-all` and `bootstrap`.
- **Floor: no session approves, merges another way or changes protection.** New deny entries in `kit/security/floor.json` cover `gh pr merge`, `gh pr review --approve`/`-a`, and the `gh api` forms of PR merges, reviews, branch merges, branch protection and rulesets, REST and GraphQL. The bash guard refuses the same forms at the start of a command. A project whose settings lack them fails `ci_security_floor` until `/zi-bootstrap --upgrade` is run.
- **Skills pass the repo as `--repo .`, not `--repo "$PWD"`.** The owner's probe run (2026-11-25, 76/77) showed Claude Code does not approve `kit lane wip --repo "$PWD"` under `Bash(kit lane wip *)`, so the skills' 40 such commands (and the planner's one) would prompt, and be refused headless. Every kit script defaults `--repo` to the working directory, so `--repo .` means the same. The probe keeps `"$PWD"` as a control (expected refused) and probes `--repo .` as approved; a test fails any skill or agent that writes `$PWD` or `$HOME` in a kit command.
- **Probe:** `npm run permissions:probe` now has a case for every rule: each allow rule, each ask and floor deny rule with a broad allow added (so only that rule can refuse), each per-run deny over the project's trusted allow rules (and inside a skill that grants plain `Bash`, as `/zi-run` does), each per-run allow through `--settings` in an untrusted repository, plus `--repo "$PWD"` in arguments and another tool called `kit`. `--only <id prefix>` re-runs a subset. Planted fault 63.

### Changed (hardening plan Step 2: rounds and wall time move into the store)
- **`lane.js advance` counts review rounds and parks a lane past the limit.** Each review → build move (a review FAIL) adds one to `failed_rounds` in the lane store (`.claude/session/lanes/<slug>.json` in the main checkout). When the move would start a round past `max_rounds` (`.claude/kit.json`, default 3; bootstrap now writes it), the lane is parked instead: stage `parked` with its reason, ROADMAP `escalated`, a `parked` event, and the move refused with the command the human runs. A parked lane refuses every move but the merge until `kit lane advance <slug> build --by <name>`, which records the name and allows one more round. The limit used to be an instruction in `/zi-review` that nothing counted (0016 C.1 #32). `/zi-review` and `/zi-run` now stop when `advance` parks the lane.
- **Wall time is the store's.** The record keeps `started` and each move's time, and the stage's budget. The budget hook reads the stage, its clock and its budget from the store, not from the lane's `lane.json`, which the lane can rewrite, and a move that re-enters its own stage no longer restarts the clock (#53). `kit_status`, the dashboard (a round pill, round and wall-time tiles, the park reason) and `next-step` show round N of the limit and the elapsed hours from the store.
- **`lane.js stage` is `advance`**, the same call and options (`--by` included), as since PR #112.
- Lanes recorded before these fields count from 0 rounds and take their start from their first move; a lane with no record shows no rounds and its budget is read from `lane.json` until its first move. Not changed: a gate FAIL does not count a round yet (there is no gate until Step 3), and `budget_override` (a human's raise, #41) is still read from `lane.json`. Planted fault 62: MISSED on main, CAUGHT here. Fault 16 now plants its low budget in the store, where it is read.

### Added (a human's security sign-off, #58, hardening plan Step 2)
- **`kit lane signoff <slug> --by <name>` records a named human's security sign-off.** A high-risk lane whose profile adds `security-signoff` (feature, fix, security, …) stopped at that stage, and `lane.js merge` refused it, with nothing able to record the sign-off. The new command writes `security_signoff` (who, when, the lane branch and its HEAD commit) into the lane store; it refuses an empty name, a lane with no commits of its own and a lane that needs no sign-off, and moves no stage. It is an `ask` rule (`Bash(kit lane signoff *)`, written by `/bootstrap` like `kit lane merge`), so Claude Code asks the human every time; the bash guard refuses its disguised forms, and the permission probe has a case for it.
- **`next-step` and `lane.js merge` accept only that record, for the commit it names.** `next-step` goes from `security-signoff` to `wait-merge` when the record matches the lane's tip; `lane.js merge` needs it to match the PR's head on GitHub and the local lane tip, and passes the signed commit to the merge, which now refuses a head that moved while CI ran (`mergeCommand`'s `head`). A later commit makes the sign-off stale: both refuse and say to review the new commits and sign off again. A sign-off written in any file (`lane.json`, progress, the spec) approves nothing. `/zi-run` pauses at `security-signoff` and runs the command only when the human says so. Planted fault 61: MISSED on main, CAUGHT here.

### Fixed (a squash-merged lane is merged, #67, #82)
- **`lane.js merged` accepts a squash-merged lane.** It required the lane tip to be an ancestor of `main`, which a squash (what `lane.js merge` does) never makes, so it refused every lane `lane.js merge` had just merged and `next-step` stayed at `wait-merge` (kit-test, project-name-constant). One function, `laneMerge` in `lane.js`, now answers for `lane.js merged`, `advance`, `kit_status`, `next-step` and the dashboard, from git and the store, with no network. A lane with commits of its own is merged when its tip is an ancestor of the base, when the store records a GitHub merge of a head holding the tip, when a commit on the base carries the patch of the lane's whole diff (a squash of one or many commits: `git cherry` compares commit by commit and misses a multi-commit squash, checked with real git), or when every lane commit has an equal patch on the base (a rebase merge). When git cannot tell (`main` not pulled), `lane.js merged` asks GitHub for the lane's PR (`--pr`, else the ROADMAP row's) and counts only `MERGED` from the lane's branch into the base at a head holding the local tip. `lane.js merge` records the merge it made (`merge`: PR, merge commit, head) in the store, with a copy in `lane.json`; only the store's copy is trusted, since `lane.json` is in the lane's worktree. A revert on `main` does not un-merge a lane (the merge happened; undoing it is new work); a lane that went on after its merge is not merged. Planted fault 58 (numbered after 56 and 57, which other work may take): MISSED on main, CAUGHT here.
- **Behaviour change:** a lane with no `start_commit` (in `lane.json` or `kit.json`; `lane.js start` has written both since the port) is no longer accepted by `lane.js merged` from ancestry alone, as `kit_status` already did not; `--pr` still lets GitHub decide. ### Fixed (the shell scope check blames a Bash call only for what that call changed)
- **Read-only commands in a sandboxed lane are no longer blocked.** In the first real-agent eval on main (516ffdd) `post-edit-check` blocked `ls … 2>/dev/null` and `npx tsc … 2>&1` twice in the retro, naming `.bashrc`, `.gitconfig`, `.mcp.json` and eight more "files changed via shell", and told the agent to `git checkout --` them. They were srt's masks: for a deny path that does not exist, srt (bubblewrap on Linux) mounts `/dev/null` on it, leaving an empty file on the host as the mount point. Git lists each one as untracked; inside the sandbox it is character device 1,3. The check took every untracked or modified path in `git status` as written by the current command, and the `>` in `2>/dev/null` was enough to run it. Reproduced with srt 0.0.83: the same eleven paths on main, none on this branch.
- **How it works now** (`kit/scripts/shell_changes.js`). `guard-bash`, once it lets a call through in a lane, records the worktree's changed paths for that `tool_use_id`. `post-edit-check` compares the state after the call with it. Without that record (a call with no `tool_use_id`) it compares with the lane's last known state, which it records after every run. Without either, only files written after the session started count (the transcript's first timestamp, else the lane stage's `started`), and no deletion does. Only regular files and symlinks count, read with `lstat`; devices, FIFOs and sockets never do. Files are compared by a hash of their content, so rewriting the same bytes (a formatter, `git stash pop`) is not a change, and a same-size write in the same timestamp tick still is. A file whose size, mtime, ctime and inode are unchanged is not hashed again, except one written in the 2 s before the previous snapshot (git's "racy" case). The state after the call is taken before the project's checks run, so files the checks write (coverage, build info) are not blamed.
- **It runs on every Bash call in a lane**, not only on commands `SHELL_WRITES` recognises, so a write through an interpreter (`node -e`, `python -c`, a formatter) is caught. Only the scope check runs on every call; whether typecheck, lint and tests run still depends on `SHELL_WRITES`.
- **An out-of-scope change stays reported until it is undone, judged on the lane's own changes.**
  - **What counts.** Each `post-edit-check` run reports the lane's out-of-scope changes, and `done-check` refuses to stop while there are any, unless the Escalation section is written (the other way out the message offers). The source is git, on every run. The lane's own changes are its diff from the merge-base of HEAD and the branch it targets: `lane.json` `base`, as `origin/<base>` else `<base>`. This is the same `<base>...HEAD` definition `ci_scope_diff` checks, so the hook and CI agree. They are:
    - commits since the merge-base;
    - the working tree;
    - untracked regular files and symlinks written after the lane was created and the session started.
  - **Merges and rebases of main.** `kit sync` (`scripts/sync.sh`) merges `origin/main` into every lane. After a merge or a rebase the merge-base moves up to main's tip, so what main brought in is never the lane's. The lane's own out-of-scope changes still differ from it and stay flagged. A conflict resolved in the merge commit counts as the lane's exactly when the result differs from main's version, as in CI. Taking main's side clears it; keeping the lane's side does not.
  - **Which base.** `base_commit` (else `start_commit`) is used when it is newer than that merge-base (a stale local ref), or when no ref resolves. With no recorded branch, `main` or `master` is tried. With none of these there is nothing to compare with: `done-check` refuses and asks the lane to record `base_commit`, rather than compare with HEAD, which would let a commit clear a change. `lane.js start` always records the base, so only old or hand-made lane.json files are affected.
  - **What does not count.** An untracked file that was already there, such as a sandbox mask or a setup's or human's file, is excluded, even if rewritten with the same bytes (`origin.json`). So are files the project's own checks wrote (`checks.json`), and the lane's own artifacts. Those come from `laneOwnedFiles`, the list `ci_scope_diff` now uses too: the progress, review, events and checks files and decision records, plus the lane's own spec when the lane created it. A fix or incident lane opens before its spec exists and the planner writes it in the lane; CI refused that spec before this change. A spec the base already has stays out of scope; guard-edit freezes it once approved.
  - **Committing does not clear a change.** A path is cleared only when its content equals the base again (or it is gone, if the base did not have it), when an untracked file that was already there has its earlier content back, or when the spec allows it. A commit that brings an out-of-scope path in is reported by the next run.
  - **`flagged.json` is a cache.** It adds which call made each change (for the wording) and an untracked file's earlier content. Every run recomputes from git, so a missing, corrupted or emptied cache changes nothing.

It still blocks. A call that never reached PostToolUse (refused or interrupted) is told apart by its result in the transcript.
