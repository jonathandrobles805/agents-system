# Changelog

All notable changes to the kit. Each entry names the decision or lesson that caused it.

## [0.3.0] - unreleased

### Changed (decision 0017: the 23 commands become 23 skills, each `zi-` plus its old name)
- **Re-run `./install.sh` after pulling.** Each command is now a skill in `~/.claude/skills/zi-<name>/`: `/run` is `/zi-run`, `/plan` is `/zi-plan`, `/review` is `/zi-review`, `/status` is `/zi-status`, `/fix` is `/zi-fix`, and so on for all 23. `install.sh` removes the kit's own old files from `~/.claude/commands/` (links are removed; `--copy` files are moved to `~/.claude/kit-backup/`; your own commands are left alone) and prints the map.
- Why the prefix: `/plan`, `/review` and `/status` are Claude Code built-in commands and `/run` is a bundled skill, which a skill of the same name replaces. `zi-` keeps every old name and clears all of them.
- `/zi-bootstrap`, `/zi-implement`, `/zi-sync` and `/zi-dashboard` are started only by a human (`disable-model-invocation: true`); the other skills hand work to each other as the commands did.
- Skill headers are valid YAML (15 of 23 were not); every description says, in the third person, what the skill does and when to use it; `/zi-implement`, `/zi-plan` and `/zi-review` name their argument (`$slug`).
- The planner no longer spawns researchers itself; the plan stage does (whether a subagent may spawn subagents depends on the Claude Code version).
- Evidence: `docs/research/claude-code-skill-probe.md` (Claude Code 2.1.327). It also found that an `allowed-tools` pattern with `"$PWD"` does not match, so the skills keep `Bash` (#63).
- **Projects:** run `node ~/.claude/kit/scripts/bootstrap.js --upgrade --all` so their CI and hook messages name the new skills.
- **Rollback:** revert the release commit, pull, delete the links `~/.claude/skills/zi-*`, and re-run `./install.sh`; the 23 old commands come back from `kit/commands/` (tested). Projects: `bootstrap.js --upgrade --all` again.


### Changed (hardening plan Step 1, D1; 0016 E.10: GitHub enforces the owner too)
- **`bootstrap --protect` sets protection nobody bypasses and reads it back.** `enforce_admins: true` (the owner included), no force push, no deletion, a pull request required but no review: `require_code_owner_reviews` is gone, because the owner says yes to each merge in Claude Code, not as a review on GitHub. After the `PUT`, the kit reads the protection back from GitHub and the result is `ok: false`, naming each difference, when GitHub holds anything else: a required check no job reports, a missing one, admin bypass on, a required review. `.github/CODEOWNERS` is still written; it only requests a review. Planted fault 30 now plants admin bypass and an unknown required check against a fake `gh` and expects both refused (it was the code-owner fault, which E.10 removed).

### Changed (0016 E.11 item 3, hardening plan Step 1: where the real-agent eval runs)
- **No credential reaches a pull request.** The real-agent smoke set moves from the pull-request job to `eval-smoke-main`, which runs on `main` after the merge over the paths the merge touched, and to the weekly full run. Both jobs declare the `main` environment, which only the `main` branch can use, and fail when neither `CLAUDE_CODE_OAUTH_TOKEN` nor `ANTHROPIC_API_KEY` arrives, instead of skipping with a notice. Pull requests keep the recorded-fixture self-check and print which gated paths they touch. Why: a pull request from a branch in this repo runs its own workflow file with the repo's secrets, so an agent's branch could read them before review; this follows GitHub's default for its own coding agent, whose PR workflows wait for a person. **Owner setup:** an environment named `main`, limited to the `main` branch, holding the two secrets; the repository-level copies can be removed once `eval-smoke-main` has run green.

### Fixed (0016 E.11, hardening plan Step 1: a matrix job's check name)
- **A matrix job is required once per value, as GitHub reports it.** `pr_gate.workflowChecks` read a matrix job's name unexpanded (`script unit tests (node ${{ matrix.node }})`), while GitHub reports one check per value (`script unit tests (node 20)`, `(node 22)`). On the kit's own repo `lane.js merge` waited for a check that never reports and stopped at its timeout, and `bootstrap --protect` would have required that name and blocked every PR. The parser now expands a single-axis matrix into one name per value; a matrix it cannot expand (`include`/`exclude`, an expression, more than one axis, or an axis the name does not use) is refused with a reason by `lane.js ci`, `lane.js merge` and `bootstrap --protect`, never guessed. Planted fault 49.

### Fixed (#68, kit-test canary run: two PRs merged on red CI)
- **Merging now waits for CI.** `lane.js merge [<slug>] [--pr N] --by <name>` is the only way the kit merges: it waits until every required job of the project's workflow has reported on the PR head and passed, refuses red or pending CI, and squash-merges pinned to the checked head (`--match-head-commit`). "No checks reported", what `gh pr checks` says before CI starts, counts as pending, not green. `lane.js ci` shows the same state without merging. `/zi-run`, `/zi-start`, `/zi-plan` and `/zi-review` use them; the bash guard blocks `gh pr merge` and merging through `gh api`.
- **Branch protection required checks that never report.** `bootstrap --protect` required step names (`scope-diff`, `review-report`, …), which GitHub never reports as checks, so every PR would have waited forever. It now requires the workflow's job names, the same list `lane.js merge` waits for.
- After merging, `lane.js merge` warns when the base branch has no protection: a merge from the GitHub page is then not blocked on red CI. Private repositories need a GitHub plan that offers branch protection.
- Planted faults 47 (an agent merges directly) and 48 (no checks or one red check read as mergeable).

### Fixed (#77, kit-test canary run)
- The `secrets` CI job failed on a pull request with `Invalid revision range` and scanned 0 bytes: its range started at the event's `base.sha`, which can name a commit that no fetched branch holds. On a pull request the range is now the checkout's first parent (the base tip GitHub merged into) to the PR head, both always in the checkout. A new `change range` step resolves the range for every event and fails with a clear message when an end is missing, instead of letting gitleaks scan nothing. Test runs the generated step in real git repos for pull request, push and merge queue.
- **Projects:** run `/zi-bootstrap --upgrade` to get the new workflow.

### Fixed (#69, kit-test canary run)
- The `review-report` CI check failed on every pull request, whatever the review said: on a `pull_request` run the checkout is GitHub's synthetic merge commit, which no review can name. The CI step now passes the PR's head commit (`PR_HEAD_SHA`), and the check compares the review with it (or with `--head`); a PR head missing from the checkout fails with a clear message instead of falling back. Pushes and merge-queue runs still compare with HEAD. Test with a synthetic-merge fixture.
- **Projects:** run `/zi-bootstrap --upgrade` (or `bootstrap.js --upgrade --all`) so their CI workflow passes the PR head.

### Fixed (field test #47, first run with real agents)
- A fix lane the debugger re-routed to refactor (`cause: design fault …`) was sent straight to `build` with 0/0 criteria: the refactor profile used the feature derivation, which reads any open lane as building. Now no profile reaches `test` or `build` while its lane has no approved, scoped spec: such a lane goes plan → approve → scope first (`inLanePlanning`), and `scope` is a script stage in every profile. End-to-end test of the re-route.

### Fixed (live run of a whole fix lane on a clone of hya-sandbox; field test #34–#46)
- Hooks find the lane from the edited file's path, not only the session's directory: a subagent started from the main checkout can now work in a lane (#37). Reads are logged where the edit guard looks.
- Red typecheck/test results count as fix attempts only in the build stage; while reproducing or writing red tests they are recorded, not fed back as "fix it" (#36, #40).
- `"none: <reason>"` commands are never run as shell commands by post-edit-check or the coverage floor (#39).
- `lane.js` run from inside a worktree works on the main checkout; sync merges base with `--no-ff`, and a lane is "merged in git" only with commits of its own (#38: a fast-forwarded empty lane looked merged).
- `sync.sh` installs dependencies when the worktree never did or a lockfile changed; it fails (exit 4) when no test command is configured (#34).
- The spec's risk raises the lane's: `next-step` reports it, and `lane.js scope` re-applies the high-risk sandbox rule (container or recorded waiver) when the spec raised the risk after the lane opened (#41).
- New `lane.js check <slug> <criterion> -- <cmd>`: run a criterion's command in the lane, log it, print the reference. The done-check now reads the exit code on a referenced line: a red run must have failed, a green run must have passed. `P<n>` criteria (preserved behaviour) need a green run only (#42, #43).
- The tester may write a file the approved spec names as a criterion's test (for example a check in a verify script) (#43).
- Lane check output moved from `docs/specs/<slug>.log` to `.claude/session/<slug>.log` (a project's structure check rejected *.log under docs/) (#44).
- Planner: the project's own required companion files (changelog, handoff, folder docs) go in Files to change (#45). Review template: R13, the project's own done gate (#46).
- Generated CI: the mutation job runs only from Actions → Run workflow unless `kit.json mutation_in_ci` is `"pr"` (cost: 10+ minutes per push on a private repo).

### Fixed (field test #32)
- The `fix` and `incident` workflows could not get past their first stage: `lane.js start` required an approved spec, which those profiles never produce, the debugger could not write its progress file without a lane, and `/run` had no row for `reproduce`. Now the lane opens from the agreed goal (`start → lane → reproduce → plan → approve → scope → test → …`); in a lane without an approved spec the edit guard allows only the progress file and the lane's own draft spec; the debugger proposes the pinning test instead of writing it; the planner writes the spec in the lane; a human approves; new `lane.js scope` validates it and copies its criteria. End-to-end test drives a fix goal from start to test; planted fault 45 (45/45).

### Fixed (first field test, hya-sandbox; decision 0014)
- Generated CI: the kit now loads through its own pinned root action (`action.yml`, `uses: <kit_repo>@<commit>`), so a private kit repo works without a token (one Actions access setting in the kit repo). Every job that runs a project command sets up its runtime and installs dependencies first (`commands.install`, detected from the lockfile). Commands are `run: |` block scalars (no more YAML or bash breakage on `:` or `(`). Workflow token is `contents: read`; gitleaks runs as a pinned, checksum-verified binary instead of `gitleaks-action`. A check with no command fails with `::error::`; `"none: <reason>"` passes with a visible warning; nothing is green by `echo`.
- New `ci_audit.js`: npm audit as a ratchet; advisories at `high` or above fail unless a named human accepted them with a reason and an expiry ≤ 90 days (`.claude/audit-baseline.json`). The old default `npm audit --audit-level=high` is migrated on upgrade.
- Bootstrap keeps the project's own hooks (merged next to the kit's, on every run and upgrade); `ci_guards_present.js` checks that every kit hook is present and unchanged and rejects a modified kit hook, instead of requiring the hooks block to equal the kit's.
- Bootstrap appends the marked kit block to an existing `CLAUDE.md` once, leaving the human text byte for byte.
- `bootstrap --upgrade` without `--answers` keeps the commands in `kit.json` (precedence detected < kit.json < answers); commands that name a kit script this kit no longer has are dropped.
- Detected commands carry their evidence; a dependency-cruiser command without a config is not proposed, and one aimed at a missing `src` scans the workspace folders that exist; a `tsc -p .` without a root `tsconfig.json` is not proposed. The `commands` question lists CI checks that are `not_configured`.
- Planted faults 39–44 (44/44); 9 tests.
- `ci_dep_diff.js`: outside a lane, a decision record changed by the branch declares new dependencies (the bootstrap PR could not pass its own check); the lane spec is read from `kit.json paths.work`, not a hard-coded `docs/specs`. Kit CI install check counts the agents instead of expecting 7.

## [0.2.0] - 2026-11-10

### Added
- `docs/OPERATING-MODEL.md` (Version 4.1): the operating model the kit is built toward; roadmap in its §16, step 0 is this release. Supersedes the phase table in `docs/implementation-plan.md` as the current plan.
- Decision 0007: the kit stays plain JavaScript with JSDoc types checked file by file; Node is the only runtime; the Python-emulation helpers remain until each has a tested native replacement.

### Changed
- `VERSION` 0.1.0 → 0.2.0, matching the approved KIT-SPEC version; `kit/architecture.json` regenerated for the new version (no other change).

### Fixed
- `bootstrap.test.js` pinned the literal `agent-kit 0.1.0`; it now reads `VERSION`, so a version bump cannot fail the suite by itself.

### Added
- Architecture Canvas on the dashboard: five views (System, Agents, Pipeline, Dependencies, Activity) over a map derived from the kit's files, with per-project overlays (hooks installed vs kit, lane stages, running agents) and a blast-radius view. Backend: `kit/scripts/arch_manifest.js`, `kit/scripts/arch_live.js`, `GET /api/architecture`, `GET /api/history`; frontend model `kit/dashboard/model.js`. The page has no external loads.
- `kit/manifest.json` (declared purpose of every command, agent, hook, check, script and CI job) and `kit/architecture.json` (committed snapshot of the derived map). Kit CI runs `npm run architecture:check`; `undeclared`, `declared-missing`, `dangling-reference`, `dangling-import`, `agent-name-mismatch`, `stage-mismatch`, `invalid-settings`, `invalid-declaration` and `unguarded-tool` fail the build.
- `npm run architecture`, `architecture:update`, `architecture:check`.
- Tests for `args.js`, `hook_notify.js` and `hook_session_context.js`, which had none (183 tests in total).

### Fixed
- The `retro` agent (Bash and Read tools) and the `spec-critic` agent (Read tool) had no PreToolUse guard of their own, against decision 0005. Found by the new `unguarded-tool` check; both now carry `hook_guard_read.js` (and `hook_guard_bash.js` for `retro`).
- Blocking hooks (`hook_guard_edit`, `hook_guard_read`, `hook_guard_bash`, `hook_guard_tests_only`, `hook_config_guard`) now run through `runGuard`: if one crashes (for example the event log cannot be written) it exits 2 and blocks, instead of exiting 1, which Claude Code treats as "carry on".
- Projects set up by an older kit version keep hooks that point at scripts that no longer exist, so their guards silently do nothing. `ci_guards_present` now names those scripts and says to run `/bootstrap --upgrade`; `install.sh` warns about every registered project in that state (`check_projects.js`). `bootstrap.js --upgrade` migrates such a project (tested).
- `lane.json` or `kit.json` containing `null`, a list or a scalar is treated as empty instead of crashing; an absolute `spec` path in `lane.json` is honoured.
- The test suite no longer writes into the developer's real `~/.claude/kit-projects.json` (each test process gets its own `CLAUDE_HOME`).

### Changed
- The whole kit is now JavaScript (Node 20+, ES modules, no npm dependencies): `kitlib`, `validate_docs`, `lane`, `kit_status`, `bootstrap`, the 12 `hook_*` scripts, the 11 `ci_*` checks, `kit/dashboard/server.js`, `planted-faults/run.js`, `audit/boards.js`, and the test suite (`node:test`, `npm test`). Every script keeps its file name (with `.js`), command-line flags, exit codes, output text and the bytes it writes; each was checked against the Python original on the same inputs before the Python was removed. Entries below that mention `.py` files describe the kit as it was when they were written.
- Hook commands in agents and in the project settings fragment, the kit CI template, `install.sh` (checks for Node 20+), `release.sh`, and the docs now call `node ... .js`.
- Python remains a supported target-project stack (detection, `stacks/python.json`, boundaries and dependency checks); only the kit's own implementation language changed.
- Removed the committed `__pycache__` files.
