This document is the contract for the kit. Nothing is built that is not described here. Anything that turns out to be needed and is not here gets added here first, then built.

Companion documents:
- `docs/research/claude-code-features.md` — verified features this spec relies on, with citations
- `docs/failure-modes-and-enforcement.md` — the control list each gate is checked against
- `docs/implementation-plan.md` — phases, order, and the check that closes each phase

---

## 1. Purpose

A reusable, versioned set of agents, commands, templates, scripts, and hooks for Claude Code that:

1. Installs once per machine and works in any repository after `/bootstrap`.
2. Runs features through a fixed pipeline: research → plan → approve → build → review → merge → retro.
3. Treats a claim about code as true only when a tool produced it, and rejects documents that violate that.
4. Blocks (not warns) the actions that cause the most damage: editing unread files, editing files outside the spec, weakening tests, committing secrets, crossing architecture boundaries.
5. Runs several features in parallel, one worktree per feature, without lanes touching the same files.
6. Learns: every mistake becomes a lesson with an enforcement level, and global lessons reach every project through a kit upgrade.
7. Shows its work: every tool call is logged by hooks, and the dashboard reads those logs, files, and git, never an agent's summary.

### Non-goals

- Replacing human approval of specs and merges. The kit minimizes those two points; it does not remove them.
- Guaranteeing correct code. The kit guarantees that incorrect code meets a gate before `main`.
- Supporting repositories that are not git repositories.
- A hosted service. Everything runs locally or in the project's CI.

## 2. Definitions

- **Kit**: this repository and what its installer places in `~/.claude/`.
- **Project layer**: files `/bootstrap` generates inside a target repository.
- **Lane**: one feature in flight: one spec, one worktree, one branch, one implementer, one reviewer.
- **Gate**: a point where work cannot proceed without a check passing. Gates are enforced by hooks, scripts, CI, or branch protection, never by an agent agreeing.
- **Claim**: any statement about how code, a library, or a system behaves. Claims carry provenance tags (section 5).
- **Evidence**: tool output, installed source at a pinned version, or official docs at a pinned version. Model memory is not evidence.

## 4. Agents

All agents are subagents in `~/.claude/agents/`. Each file has: frontmatter (`name`, `description`, `tools` or `disallowedTools`, `model`, `hooks` where noted), a role statement, hard rules, the template it fills, and forbidden behaviors. Each file is capped at 120 lines so it is read, not skimmed.

### 4.1 `researcher`

- Input: exactly one question, the research INDEX, repo access, web access, installed package source.
- Tools: Read, Grep, Glob, Bash (read-only commands), WebSearch, WebFetch. No Edit/Write except to its own output file.
- Output: `docs/research/<slug>.md` in the research template, and an INDEX entry.
- Hard rules: every finding carries a tag; every `[verified: path:line]` must have been read in this session; library claims carry `@ version` from the lockfile; unknowns get a resolution method; hedge words are not permitted in Findings.
- Refuses: more than one question; writing outside its output file; untagged findings.
- Hooks (frontmatter): `SubagentStop` runs `validate-docs` on the output file; failure feeds the errors back and the agent must fix them before it may stop.

### 4.2 `planner`

- Input: research files for the topic, `ARCHITECTURE.md`, `DESIGN.md`, `LESSONS.md`, `ROADMAP.md`, every open spec.
- Tools: Read, Grep, Glob, Bash (read-only: `git grep`, references), Write to its own spec file only.
- Output: `docs/specs/<feature>.md` in the spec template.
- Hard rules: impact analysis lists every caller of every changed symbol with `file:line`; each done-criterion names a test; assumptions are verified or moved to open questions; unknowns 1–3 become verification tasks and the planner runs them (spawning researchers) before finishing; more than 3 unknowns → planner stops and reports "research insufficient"; file lists are compared with every open spec and any overlap is refused; WIP limit from `.claude/kit.json` is checked; architecture checklist from `ARCHITECTURE.md` is copied in and answered; new dependencies and data changes are declared; risk flag is set by `validate-docs` from paths and keywords.
- Refuses: writing a spec with open questions; overlapping files; WIP exceeded; done-criteria without tests.
- Hooks: `SubagentStop` runs `validate-docs` on the spec.

### 4.3 `spec-critic`

- Input: the spec and the research it cites. Nothing else.
- Tools: Read, Grep. No Write except appending a `Critique` section to the spec.
- Output: numbered list of gaps, contradictions, missing callers, untested criteria, and risks the spec understates.
- Refuses: approving; rewriting the spec; reading the planner's conversation.

### 4.4 `implementer`

- Input: the approved spec, `LESSONS.md`, the files the spec lists.
- Tools: Read, Grep, Glob, Edit, Write, Bash.
- Output: code, tests, `docs/specs/<feature>.progress.md`, commits in its worktree.
- Hard rules: reads every file in the spec's "read first" list before any edit; writes tests for each done-criterion before the code and runs them red; updates `progress.md` after each done-criterion turns green; stops after 3 failed fix attempts on one failure and writes an escalation section in `progress.md`; never edits a file outside the spec's file list; never adds a dependency not declared in the spec; never touches `.claude/settings.json`.
- Hooks (frontmatter and project settings):
  - `PreToolUse` on `Edit|Write` → `guard-edit` (blocks unread or out-of-spec paths, exit 2)
  - `PreToolUse` on `Bash` → `guard-bash` (blocks `git push --force`, destructive commands, edits to settings, writes outside the worktree)
  - `PreToolUse` on `Read` → `guard-read` (blocks `.env*`, key files, credential directories; see 10.1)
  - `PostToolUse` on every tool → `budget-check` (time and token budget per stage; see 10.2)
  - `PostToolUse` on `Edit|Write|Bash` → `post-edit-check` (typecheck, lint, affected tests, assertion/skip diff; writes to `.log`; `decision: block` with the failure text on red)
  - `PostToolUse` on every tool → `event-log` (appends to `.events.jsonl`)
  - `Stop` → `done-check` (refuses to stop if progress.md is stale, if any done-criterion lacks a green run in the log, or if an escalation is required but not written)
  - `ConfigChange` → blocks changes to project settings during a lane

### 4.5 `reviewer`

- Input: the spec, the diff against `main`, `.log`, `.events.jsonl`, `ARCHITECTURE.md`, `DESIGN.md`, `LESSONS.md`. Never the implementer's conversation.
- Tools: Read, Grep, Glob, Bash (run tests and lints; no edits to source), Write to `docs/specs/<feature>.review.md` only.
- Output: review report in the review template: a checklist with PASS/FAIL per item and evidence (`file:line` or log line), plus a fail list in the required form.
- Checklist (minimum): every done-criterion has a named test with a red run and a green run in the log; the reviewer re-ran the suite and the result matches the log; every changed file is in the spec's list; no assertion removed or test skipped without a spec note; import boundaries respected; design tokens respected; new dependencies declared; data changes reversible or signed off; `progress.md` complete; reviewer wrote at least one adversarial test from the spec and it passes.
- Refuses: PASS without evidence; reading the builder's reasoning.
- Hooks: `SubagentStop` runs `validate-docs` on the review report.

### 4.6 `retro`

- Input: merged PR, review report, progress file, events log, `LESSONS.md`.
- Output: a lesson entry in the lesson template with `Enforced by` set to one of `hook | lint | test | ci | text-only`, and when not text-only, the concrete change (a hook rule, a lint rule, a test template) as a proposed diff for you to approve.
- Refuses: a lesson without an enforcement proposal unless explicitly marked text-only debt with a reason.

## 5. Provenance and `validate-docs`

### 5.1 Tags

Every finding, assumption, or claim in a research file, spec, or review report carries exactly one tag:

- `[verified: <path>:<start>-<end>]` — the cited lines exist and the claim is about them
- `[verified: cmd]` followed by a fenced block with the command and its output
- `[docs: <url> @ <version>]`
- `[inferred: from <ids>]` — reasoning from tagged claims, listing them
- `[unknown]` followed by `Resolve by: <method>`

### 5.2 Rules `validate-docs` enforces

1. Required sections present for the document type.
2. Every bullet under Findings, Assumptions, Impact, and Checklist carries a tag.
3. Every `[verified: path:line]` resolves: file exists at the recorded commit, lines in range, and when a quoted snippet is present it matches the file.
4. No decision in a spec (Files to change, Approach, Data changes) rests on `[inferred]` or `[unknown]` claims.
5. Hedge words (`should`, `probably`, `likely`, `I think`, `assume`) are not allowed in Findings or Impact unless the line is tagged `[unknown]`.
6. Spec: each done-criterion has a test name; Open questions is empty before approval; file list is non-empty; Assumptions section present; Non-goals present.
7. Spec risk flag: `high-risk` is set when any listed file matches the project's high-risk paths (`.claude/kit.json`) or the spec mentions auth, payment, delete, migration, public API, secrets.
8. Research: date, commit hash, Confidence, and "What I could not verify" present; INDEX entry exists.
9. Review report: every checklist item is PASS or FAIL with evidence; every FAIL has file, line, rule, and what passing looks like.

Exit code 2 with the list of violations on stderr. Runs as a `SubagentStop` hook for the three writing agents, as a `PostToolUse` hook on writes under `docs/`, and in CI.

## 6. Commands

Each command is a Markdown file in `~/.claude/commands/`. Preconditions are checked by a script the command calls first; if a precondition fails, the command stops and prints why.

| Command | Preconditions | Steps | Output |
|---|---|---|---|
| `/bootstrap [--upgrade]` | git repo; not bootstrapped unless `--upgrade` | detect stack → generate project layer from templates → draft ROADMAP, ARCHITECTURE, DESIGN from what it finds → ask you the questions in 7.3 → write `.claude/kit.json` → set branch protection via `gh` → run CI once | project layer, kit version stamp |
| `/research <topic>` | bootstrapped | read INDEX → for each question: reuse (same commit), re-verify (cited files changed), or spawn researcher → parallel spawn → update INDEX | research files |
| `/plan <feature>` | research exists; WIP limit not hit | run planner → resolve unknowns → run spec-critic → write spec with one-screen summary | spec, status `waiting-approval` in ROADMAP |
| `/implement <feature>` | approval line present; Open questions empty; `main` fetched | create worktree `wt/<feature>` from fresh `main` → `/sync` → run implementer with lane hooks → on `done-check` pass, push branch and open PR | PR, progress file, log, events |
| `/review <feature>` | PR exists | run reviewer → if `high-risk`, run second reviewer with a different model and the security/data checklist → write report → post fail list to PR | review report |
| `/sync` | in a worktree | `git fetch`, merge `main`, run tests, report | — |
| `/retro <feature>` | PR merged | run retro agent → show proposal → on your yes, write lesson and apply the proposed check | LESSONS entry, optional hook/lint/test change |
| `/status` | — | run `kit-status` → print ROADMAP, lanes, drift, waiting-on-you, debt | status.json and console summary |

Worktree creation also fires the `WorktreeCreate` hook, which copies the lane's `.claude/settings.json` and records the lane in `.claude/kit.json`.

## 7. `/bootstrap` detail

### 7.1 Detection matrix

| Signal | Detected | Mapped to |
|---|---|---|
| `package.json` | Node; framework from deps (Next, React, Express, ...) | test: jest/vitest; typecheck: tsc; lint: eslint; boundaries: dependency-cruiser; tokens lint: stylelint or eslint rule; mutation: stryker |
| `pyproject.toml` / `requirements*.txt` | Python; framework from deps | test: pytest; typecheck: mypy/pyright; lint: ruff; boundaries: import-linter; mutation: mutmut |
| `go.mod` | Go | test: go test; lint: golangci-lint; boundaries: depguard |
| `Cargo.toml` | Rust | test: cargo test; lint: clippy |
| other | unknown | bootstrap asks you for the commands |
| `.github/` | GitHub Actions | `kit.yml` |
| `.gitlab-ci.yml` | GitLab | `.gitlab-ci-kit.yml` include |
| none | — | asks |

Tools not installed are listed; bootstrap proposes adding them and does not add them without your yes.

### 7.2 Generated hooks (`.claude/settings.json`)

- `PreToolUse` `Edit|Write` → `guard-edit`
- `PreToolUse` `Bash` → `guard-bash`
- `PreToolUse` `Read` → `guard-read`
- `PostToolUse` `.*` → `budget-check`
- `Notification` and `Stop` → `notify` (see 10.3)
- `PostToolUse` `Edit|Write|Bash` → `post-edit-check`
- `PostToolUse` `.*` → `event-log`
- `PostToolUse` `Write` with `if: Write(docs/**)` → `validate-docs`
- `Stop` → `done-check` (active only when `.claude/kit.json` marks the cwd as a lane)
- `SessionStart` `compact` → re-inject the lane's spec summary and `LESSONS.md` top section
- `ConfigChange` → block `project_settings` changes while a lane is active

### 7.3 Questions bootstrap asks you (and does not guess)

1. Milestones and the first five features for `ROADMAP.md`, from its draft.
2. WIP limit (default 2).
3. Architecture layers and the dependency direction between them, from its draft.
4. High-risk paths (default: auth, payments, migrations, public API, infra).
5. Which detected tool commands are correct.

### 7.4 Generated CI (`kit.yml`)

Jobs on every PR: tests; typecheck; lint; import boundaries; `scope-diff` against the spec named in the branch; `test-count` vs `main`; `dep-diff`; secret scan; `claude-md-cap`; `guards-present`; `validate-docs` on changed docs; review-report check (report exists for the PR's head commit with all PASS); mutation score on changed files (threshold from `kit.json`, default 70%, warning-only for the first two features then blocking); PR size warning.

Branch protection via `gh api`: required checks = all of the above; strict up-to-date; no force push; no direct pushes to `main`.

## 8. Templates (required sections)

- **research**: Question · Date · Commit · Findings (tagged) · What I could not verify · Confidence · Recommendation · Sources
- **spec**: Summary (one screen: goal, files changed, risks, done-criteria) · Goal · Non-goals · Files to read first · Files to change (with extension points) · Impact analysis · Approach · Data changes · New dependencies · Done-criteria → test names · Assumptions · Open questions · Architecture checklist · Risk flag · Critique · Approval line
- **progress**: Done-criteria table (criterion, test, red run ref, green run ref) · Current step · Uncertainties · Escalation (attempts, failure, what was tried)
- **review**: Scope · Checklist (PASS/FAIL + evidence) · Adversarial tests added · Fail list · Verdict
- **lesson**: Date · Feature · What went wrong · Root cause · Rule · Enforced by · Proposed change · Status
- **roadmap**: Milestones · WIP limit · Features table (name, status, spec, lane, PR) · Queue
- **decision**: Context · Decision · Alternatives rejected · Consequences
- **INDEX**: table of question, slug, keywords, files cited, commit, date, status

## 9. Event log and dashboard

### 9.1 Event schema (`docs/specs/<feature>.events.jsonl`, one JSON object per line)

`ts`, `session_id`, `lane`, `event` (`read | edit | write | bash | test | lint | typecheck | blocked | hook_fail | stop_refused | subagent_start | subagent_stop`), `tool`, `path` or `command`, `summary` (first line of output), `result` (`ok | fail | blocked`), `ref` (pointer into `.log` when output is long).

Written only by the `event-log` and `post-edit-check` hooks. Agents never write to it.

### 9.2 `kit-status`

Produces `status.json` from `ROADMAP.md`, specs, progress, review reports, logs, events, `LESSONS.md`, `git worktree list`, `git rev-list --count main..HEAD`, and the last CI result via `gh`. Lane position is derived: spec without approval line → waiting-approval; worktree with progress and no review → building; review all PASS and CI green → ready-to-merge; progress has Escalation → escalated.

### 9.3 Dashboard

- Static mode: `dashboard/index.html` renders `status.json`; CI publishes it to GitHub Pages on every push.
- Live mode: `dashboard/server` (Node) watches the files, pushes updates over a websocket, streams `.events.jsonl`, and exposes "open Claude in this worktree", which launches `claude` in the lane's directory, resuming that lane's session.
- Index page across projects: `kit-status --all` reads a list of project paths from `~/.claude/kit/projects.json`.

## 10. Acceptance criteria

The kit is done when all of the following hold:

1. `install.sh` on a clean machine results in all agents and commands visible in `/agents` and `/help`.
2. `/bootstrap` on two unrelated repos produces the project layer, CI passes on `main`, and branch protection is set.
3. One small feature per repo goes from `ROADMAP.md` to merged PR with your only actions being spec approval and merge.
4. Every planted fault below is caught at the gate that owns it, and the catch is visible in the events log and the dashboard.
5. `/retro` on one feature produces a lesson whose proposed check, once applied, still passes the planted-fault run.
6. The dashboard shows the correct lane position for every lane in both repos without any agent-reported field.

### Planted faults

| # | Fault | Owning gate | Expected |
|---|---|---|---|
| 1 | Edit a file never read | `guard-edit` (PreToolUse) | blocked, event `blocked` |
| 2 | Edit a file outside the spec | `guard-edit`; `scope-diff`; reviewer | blocked; CI fail; FAIL item |
| 3 | Delete an assertion to pass | `post-edit-check`; `test-count`; reviewer | block decision; CI fail; FAIL |
| 4 | Import across an architecture boundary | boundaries lint (hook + CI) | red in hook; CI fail |
| 5 | Change a function, miss a caller | typecheck or tests in hook; CI | red; CI fail |
| 6 | Research cites a line that does not exist | `validate-docs` on SubagentStop | agent must fix before stopping |
| 7 | Spec with an unresolved unknown | `/implement` precondition | refused |
| 8 | Undeclared dependency added | `dep-diff` | CI fail |
| 9 | Secret committed | `guard-bash` on commit; secret scan in CI | blocked; CI fail |
| 10 | `CLAUDE.md` over cap | `claude-md-cap` | CI fail |
| 11 | Hook removed from settings | `ConfigChange` hook; `guards-present` | blocked during lane; CI fail |
| 12 | Implementer says done with a criterion still red | `done-check` (Stop) | stop refused |
| 13 | Two specs list the same file | planner overlap check | second spec refused |
| 14 | Reviewer writes PASS with no evidence | `validate-docs` on review report | agent must fix |

| 19 | Dependency with a known vulnerability added | vulnerability scan in CI | CI fail |

## 10.1 Running unattended: permissions

Claude Code asks for permission on tools by default, which would turn every lane into a prompt waiting for you. Each lane therefore runs with a permission profile generated by `/bootstrap` into `.claude/settings.json` under `permissions`:

- `allow`: the tools listed in the active agent's frontmatter, scoped by pattern where possible (`Edit(src/**)`, `Bash(npm test *)`, `Bash(git commit *)`).
- `deny`: `Read(.env*)`, `Read(**/*.pem)`, `Read(**/secrets/**)`, `Bash(git push --force*)`, `Bash(rm -rf *)`, `Edit(.claude/**)`, `Bash(curl *)` and `Bash(wget *)` unless the spec declares network access.
- Everything not listed falls to `ask`, which in an unattended lane means the lane pauses and writes an escalation. That is the intended behavior: an unexpected tool is a signal, not something to auto-approve.

Lanes never hold production credentials. `/bootstrap` checks for credential files in the repo and refuses to generate a lane profile that can read them.

## 10.2 Budgets

`.claude/kit.json` holds per-lane budgets: wall-clock hours per stage (default research 1, plan 1, build 4, review 1) and a token budget per stage. `budget-check` runs as a `PostToolUse` hook on every tool call; when a budget is exceeded it writes an escalation to `progress.md` and the `Stop` hook ends the lane. Budgets are raised in the spec, not in the moment.

## 10.3 Notifications

A `Notification` hook and the `Stop` hook send a message when: a spec is waiting for approval, a PR is ready to merge, a lane escalated, a budget was exceeded, or CI went red on `main`. Channel is configured in `~/.claude/kit/notify.json`: desktop notification by default, with optional Slack webhook or email. The dashboard shows the same items; notifications exist so you do not have to look.

## 10.4 Model per agent

Frontmatter `model` per agent, overridable in `.claude/kit.json`: researcher and `event-log` summaries on the cheapest capable model; planner, implementer, and reviewer on the strongest available; second reviewer for `high-risk` on a different model family when one is configured, otherwise the same model with a different checklist. `/status` reports cost per lane from the events log.

## 10.5 Merge conflicts

`/sync` runs at lane start and at least daily. On conflict: the implementer may resolve once, with the conflict treated as a failed test that counts against the 3 attempts, and must re-run the full suite afterward. A second conflict in the same lane, or any conflict touching a file outside the spec, is an escalation.

## 10.6 Non-code features

For a feature whose output is not code with tests (design, documentation, configuration), the spec's done-criteria name a reviewable artifact and a checklist instead of a test. The reviewer checks the artifact against the checklist and `DESIGN.md`. `validate-docs` accepts either form but not an empty one.

## 10.7 Script integrity

Every kit script has unit tests in `kit/scripts/tests/`. The kit's own CI runs them plus the planted-fault suite on every change; a release is blocked if either fails. `guards-present` in each project compares the installed scripts' hashes to the kit version's manifest, so a modified or missing script fails CI.

## 10.8 Supply chain

CI runs a vulnerability scan on the lockfile (`npm audit`, `pip-audit`, `cargo audit`, `govulncheck`, or the provider's equivalent) and fails on high severity. `dep-diff` already fails on undeclared dependencies.

## 11. Versioning and upgrades

- `VERSION` follows semver. `CHANGELOG.md` records every change with the lesson or decision that caused it.
- `/bootstrap` stamps the kit version into `CLAUDE.md` and `.claude/kit.json`.
- `/bootstrap --upgrade` first runs the planted-fault suite against the project's current configuration, backs up every file it will replace into `.claude/backup/<version>/`, diffs generated files against the current templates, shows the changes, and applies them on your yes. Files you edited by hand are merged, not overwritten. It then re-runs the planted-fault suite and reverts from the backup if any fault is no longer caught.
- `/status` warns when a project is more than one minor version behind.

## Approval

To approve, replace the header fields with your name, the date, and the commit hash, and merge this PR. Phase 1 starts from that commit.
