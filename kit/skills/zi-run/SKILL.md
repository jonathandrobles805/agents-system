name: zi-run
description: "Carries a feature through every stage (research, spec, approval, tests, build, review, merge, retro), asking kit lane next-step what comes next each time and stopping only where a human must act. Use to start or resume work on a feature that has an agreed goal, or with --queue to work through the roadmap."
argument-hint: "<feature slug> | --queue"
allowed-tools: Bash, Read, Edit, Agent, AskUserQuestion
---

Run: $ARGUMENTS

You orchestrate. You never write application code, tests, specs, reviews, or lessons yourself; every stage is a subagent or a kit script. You never guess what stage comes next; you ask the script. Only `kit lane advance` moves a lane's stage, and it refuses a move its table does not allow or the lane's files do not justify; relay its reasons. You stop only at `needs_human`, at `escalated`, or at `done`. Relay script refusals verbatim; never work around a precondition.

## The loop (one feature)

```
kit lane next-step <slug> --repo .
```
Read `stage` and act as below, then run `next-step` again. Repeat until `done`, or until a stage below says stop. The answer also carries `work_type`, `size`, `risk` and `agent`: the one agent the workflow profile allows for this stage (`kit/workflows/<work_type>.json`). Spawn that agent and no other; when `agent` is null the stage is the human's or a script's. A `rerouted` field means the controller changed the work type from the debugger's evidence; continue under the new profile. A stage below that the profile lacks will never be returned for that work type.

| stage | what you do |
|---|---|
| `start` | Stop. Say: "no agreed goal; run `/zi-start`". Never invent a goal. |
| `research` | `kit lane goal-set <slug> running`; `kit lane roadmap-set <slug> researching`. Derive 2–5 questions from the goal's *Done looks like* and *Constraints* (how the relevant code works today, what calls what, external APIs at pinned versions, existing tests). Follow the `/zi-research` procedure exactly: index lookup per question, researchers in parallel, register, validate. |
| `plan` | fix/incident: spawn `planner` (working directory = worktree): "Lane `<slug>`. Write docs/specs/<slug>.md from the goal and progress.md ## Reproduction: Files to change from its `files:` list, one done-criterion per *Done looks like* item plus the pinning test it proposes. Set status waiting-approval. Stop." Then validate_docs and stop for approval. Otherwise follow `/zi-plan` steps 2–4 exactly: planner → `kit lane unknowns` (exit 2: stop and tell the human research is insufficient; exit 3: a researcher per item, then planner again) → spec-critic → planner answers → `validate_docs` → `kit lane precheck` failing only on approval. `kit lane roadmap-set <slug> waiting-approval`. The planner must map every `G<n>` in the goal to a done-criterion; an unmapped outcome is a critique item. |
| `approve` | **Pause 1.** Print the spec's `## Summary` and the Critique items with answers. AskUserQuestion: Approve / Changes / Stop. *Changes*: give the human's text to the planner as a critique item and go back to `plan`. *Stop*: `roadmap-set <slug> queued`, `goal-set <slug> agreed`, end. *Approve*: edit the spec header to `Status: approved` and leave its Approval section as it is (nobody writes the approval; `kit lane merge` records it); commit spec, research, ROADMAP on branch `spec/<slug>` (fix/incident: the spec is in the lane; set the status there and put that exact file on the branch, since `kit lane scope` refuses a lane spec that differs from the merged one); `kit lane publish <slug> --branch spec/<slug> --title "spec: <feature>" --body-file <a file holding the spec's Summary, e.g. /tmp/<slug>-summary.md>` (pushes and opens the PR as the kit's GitHub App; prints the URL); merge it with `kit lane merge --pr <url> --by <approver>`: Claude Code asks the human first, and the merge records their yes (who, when, the merged commit) in the lane store, the only approval `kit lane start` and `kit lane scope` accept. It waits for CI and merges only when every required check passed; if it refuses, show its reasons and stop. |
| `lane` | `kit lane start <slug>` then `cd <worktree> && bash scripts/sync.sh`. Exit 3 from sync is a conflict: that counts as the lane's first attempt; a second conflict is an escalation. Exit 4: no test command is configured, so nothing proves the lane passes; stop and ask the human for one. Sync installs dependencies itself when the worktree has none or a lockfile changed. |
| `test` | `kit lane advance <slug> test`. Spawn `tester` (working directory = worktree): "Lane `<slug>`. Write the tests for every done-criterion and their negative/edge cases per your rules. Run them red. Fill the Red run column. Stop." Its Stop hook refuses until every criterion has a red run. |
| `build` | `kit lane advance <slug> build`: it refuses until every criterion cites a logged red run of its test; give the tester its reasons and run the `test` row again. Spawn `implementer` (working directory = worktree): "Lane `<slug>`. Read lane.json, the spec, every file in Files to read first and Files to change, LESSONS.md, and the tests the tester wrote. They are red; make them green at the extension points the spec names, criterion by criterion, without changing their assertions. Update progress.md and commit after each. Stop when every criterion is green or Escalation is filled." The hooks count attempts and write the escalation themselves. |
| `gate` | `kit lane gate <slug>`: it re-runs the project's recorded checks (the base branch's `.claude/kit.json` commands, never the lane's) on the lane's HEAD, contained, with a time limit and stdin closed, and records the verdict for that commit. Exit 0 (`GATE: PASS`): run `next-step` again. Exit 1 (`GATE: FAIL`): run `next-step`; when it says `escalated` (the risk re-check: a lane not approved as high risk changed a high-risk path), stop for the human. Otherwise spawn `implementer` (working directory = worktree) with only the report it printed: "Lane `<slug>`. The gate failed: <report>. Fix exactly these, commit, then stop." Then `next-step` again. A FAIL counts as a failed round; when the lane parks (`escalated`), stop for the human. Exit 2 (refused): relay its reason (uncommitted changes: the implementer commits them). A `protected-files` FAIL (the lane changed its spec, `.claude/`, CI configuration, a package.json `scripts` entry or test configuration) goes to the implementer to undo; such a change is the human's, outside the lane. Never spawn a reviewer on anything but a PASS for the lane's HEAD. |
| `review` | If the lane has no PR yet: `kit lane publish <slug>` (pushes `wt/<slug>` and opens the PR as the kit's GitHub App, never with your login; it prints the PR URL), `kit lane roadmap-set <slug> in-review --pr <url>`. Then `kit lane advance <slug> review` (it refuses until every criterion cites a logged green run of its test and the gate passed the lane's HEAD; give the implementer its reasons, or run the `gate` row) and follow `/zi-review` exactly (second reviewer on high-risk; fail list back to the implementer; when `advance` parks the lane after its last round, stop for the human). |
| `wait-merge` | **Pause 2.** Run `kit lane ci <slug> --wait` and tell the human: PR link, the CI state it prints (never from `gh pr checks`, which says "no checks reported" before CI has started), verdict, and from the events log the counts of edits blocked, red runs, green runs, stop refusals. Ask whether to merge. **Merge only when they say so**, and only with `kit lane merge <slug> --by <their name>`: it waits for every required check on the PR head and refuses red or pending CI. Never `gh pr merge` (the bash guard blocks it). If it refuses, show the reasons and stop. In `--queue` mode continue other lanes and come back; otherwise end the turn here. |
| `retro` | `git fetch origin && kit lane merged <slug> --repo . --pr <url>`. Follow `/zi-retro`: retro agent proposes; AskUserQuestion per lesson (accept / edit / drop); write accepted ones; `kit lane finish <slug>`; `kit lane goal-set <slug> done`. |
| `escalated` | Stop. Show the `reason` next-step gives and, when progress.md has one, its Escalation section verbatim. `roadmap-set <slug> escalated`. A human decides. |
| `stopped` | Stop. The kill switch is set (`.claude/STOP`); show its `by` and `reason`. Nothing runs until a human runs `kit lane resume-all --by <name>`. |
| `security-signoff` | **Pause.** The lane is high risk and needs a named human's security sign-off before the merge. Show the reason verbatim, the PR link and the review verdict, and ask the human whether they sign off this lane's HEAD. **Only when they say so**, run `kit lane signoff <slug> --by <their name>`: Claude Code asks them first, and it records who, when and the lane's HEAD commit in the lane store, the only sign-off `next-step` and `kit lane merge` accept. Never write a sign-off into a file; it counts for nothing. A commit after the sign-off makes it stale: next-step comes back here and `kit lane merge` refuses until they sign off again. Never merge it another way. |
| `refused` | Stop. Show the reason verbatim: the goal's `Work type` has no profile, its work type is not built yet, or a stage has no equivalent in its profile. The human decides; never pick a profile yourself. |
| `done` | Report: PR, lessons written, debt count from `/zi-status`. |
| `reproduce` | fix/incident only. `kit lane advance <slug> reproduce`. Spawn `debugger` (working directory = worktree): "Lane `<slug>`. Reproduce the goal's symptom, localize the cause, propose the pinning test and list the files the fix needs, all in progress.md under ## Reproduction, ending with one `cause:` line. Stop." It can write only the progress file. |
| `scope` | fix/incident only, after the human approved the spec the planner wrote in the lane: `git fetch origin && kit lane scope <slug>`. It refuses unless the spec's `spec/<slug>` PR was merged with `kit lane merge` (which recorded the approval), the lane's spec is the merged one, and it is valid and overlaps no other lane; then it copies the done-criteria into progress and moves the lane to test. |

## Queue mode (`--queue`)

```
kit lane next --repo .
```
Exit 0 gives the next slug with an agreed goal under the WIP limit; run the loop for it. Exit 2 says why not (WIP full or no agreed goal). Run independent lanes in parallel: spawn their stage agents in the same turn, each with its own worktree as working directory. A pause in one lane never blocks the others. Stop when `next` returns exit 2 and every in-flight lane is at a pause.

## What the human sees

`/zi-start`, a short discussion, then "approve", "merge", "accept". Everything else is this loop, the agents, and the hooks. `/zi-dashboard` shows all of it live, from the same files `next-step` reads.
